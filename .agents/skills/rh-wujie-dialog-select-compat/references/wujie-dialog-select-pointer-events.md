# Wujie 子应用中 Dialog / Select 的 pointer-events 问题复盘

## 适用范围

只要任务涉及下面任一情况，都要先看这份复盘：

- `Dialog` 里嵌套 `Select`
- Wujie 子应用
- 弹窗里切换下拉选项后无法继续点击
- 节点被错误加上 `pointer-events: none`

## 现象

- 作为子应用访问时，弹窗里打开 `Select`
- 切换选项后，外层 `dialog` 内容突然失去交互
- 实际看到的是弹窗内容节点被错误加上了 `pointer-events: none`

## 真实原因

根因不在业务页面，而在通用弹层链路。

在 Wujie 子应用里，`Dialog` 和 `Select` 都属于弹层组件。
当 `Dialog` 内再打开 `Select`，并且用户切换选项时，底层弹层管理会处理"谁是当前活动层、哪些区域应该禁点"。
这套逻辑在普通环境下通常没问题，但在 Wujie 子应用里，宿主容器和 shadow DOM 的关系会让这套判断偶发失真，结果就是：

- 本来应该只作用在外层区域的"禁点"限制
- 被错误打到了 `dialog` 内容节点本身
- 从而导致弹窗内容失去点击能力

## 为什么不能只在业务页面修

因为这不是某一个页面自己的问题，而是一个通用组合问题：

- `Dialog` 可复用
- `Select` 可复用
- Wujie 环境也是全局性的

如果只在当前页面单独补样式或补判断：

- 下一个弹窗还会再中一次
- 新页面还是会重复踩坑
- 维护成本会越来越高

## 最佳修复方案

最佳方案是"组件内部统一修 + 样式层兜底"，两层一起做。

### 1. 组件内部统一修

在通用弹窗层做保护，也就是 `rh-theme/overlays`：

- 保留对 `body` 的修复
- 再额外监控弹窗内容节点本身
- 一旦发现子应用环境里弹窗内容被错误加上 `pointer-events: none`
- 立刻恢复成可交互

这样以后所有走这套弹窗的页面，都会自动吃到修复。

### 2. 样式层兜底

在全局样式里只对 Wujie 子应用生效：

- `.rh-dialog-content`
- `.rh-alert-dialog-content`

强制保证这两个弹窗内容区域始终可点击。

这样即使底层链路又偶发打错样式，最终仍然不会锁死弹窗。

## 不推荐的修法

不要优先选这些方案：

- 在某个业务页面里手动删样式
- 每个表单页都各自补一段 `pointer-events: auto`
- 只改当前页面，不改通用弹窗层
- 继续把问题归因到页面状态管理，而忽略弹层组合本身

这些做法都太散，后面很容易漏掉。

## 排查顺序

再遇到类似问题时，按这个顺序排查：

1. 先确认是否是 Wujie 子应用环境
2. 看是否是 `Dialog` 里再打开了 `Select`
3. 在浏览器里检查是不是弹窗内容节点被加了 `pointer-events: none`
4. 如果是，优先回通用弹窗层修，不要先在业务页打补丁
5. 最后再看页面是否还有别的状态或事件链路问题

## 一句话结论

这是"子应用环境 + 弹窗内下拉"引发的通用兼容问题。
最佳修复方案是放在通用弹窗层统一处理，再用全局样式做兜底，而不是在单个业务页面零散修补。
