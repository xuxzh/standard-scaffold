# 应用 UI 规范

本文档定义当前脚手架在 `apps/web` 中实现界面时的默认 UI 约束。它面向日常开发和 AI 执行，目标是减少界面结构和交互模式上的随意性。

## 壳层与页面结构

### 默认围绕应用壳层组织页面

应用壳层围绕 `AdminLayout`、`AppHeader` 和 `AppSidebar` 组织。新增页面或页面级功能时，应优先复用这一结构，而不是并行再造新的主壳层。

如果某个页面需要脱离壳层，例如登录页、引导页或嵌入式页面，应在对应 spec 或 route 设计中明确说明原因。

### 页面内容区优先表达业务内容，而不是再次实现导航骨架

页面主体应关注业务信息层次、操作入口和状态反馈。除非设计明确需要，不要在页面内重复实现一级导航、全局标题区或全局筛选骨架。

## 组件复用优先级

### 先复用应用本地基础组件

涉及 `apps/web` 的界面开发时，优先复用 `apps/web/src/components/ui` 中已有的 shadcn 组件和本地封装组件。

如果仓库中缺少合适的通用组件，优先按现有项目方式拉取对应的 shadcn 组件，而不是从零实现相近能力。

### `packages/ui` 不是默认落点

除非组件明确需要跨应用或跨 workspace 共享，否则不要把应用内局部组件迁移到 `packages/ui`。先在应用内验证模式稳定，再考虑上提。

## 页面常见状态规范

### Loading

- 首屏加载应给出明确反馈，不要出现长时间空白。
- 局部刷新优先用就地反馈，避免不必要地重置整页内容。
- Skeleton、占位符或按钮内 loading 状态应与操作粒度一致。

### Empty

- 空态应说明“为什么现在是空的”以及“用户下一步可以做什么”。
- 不要只显示一个空白容器或孤立图标。

### Error

- 错误态应尽量给出可执行的下一步，例如重试、返回或检查输入。
- 不要直接向用户暴露未经处理的原始报错对象。

### Disabled

- 禁用态需要让用户理解不可操作的原因；如果原因不明显，应补充上下文或说明。
- 不要用纯视觉弱化替代真实禁用语义。

## 可访问性最低要求

- 交互元素优先使用语义化 HTML 或已有无障碍基础组件。
- 表单控件需要可感知的标签、说明或等效无障碍名称。
- 图标按钮、仅图形操作和状态切换控件必须能被读屏识别。
- E2E 和组件测试优先使用 `getByRole` 和稳定可见文案定位，这也要求界面本身提供可访问的角色和名称。

## 响应式与密度

- 新增页面或大块内容区时，应至少考虑桌面和移动两档布局是否仍可用。
- 不要把桌面端多列布局原样压缩到窄屏；必要时改为堆叠、抽屉或分步展示。
- 数据密度高的区域优先保证可读性和操作清晰度，不为追求“塞更多信息”牺牲层次。

## 文案与交互一致性

- 同一类动作应尽量复用一致的命名，例如“新建”“保存”“删除”“重试”。
- 成功、失败、警告、确认等反馈语气应在同一页面和相邻页面中保持一致。
- 不要把临时调试文案、英文占位符或和领域无关的通用标题直接带到用户界面。

## 与测试的关系

- UI 规范不是只给设计看的，用户可见状态需要能被测试验证。
- 组件测试或 route 测试应覆盖关键状态分支。
- 涉及壳层、导航、主题、语言或关键主链路交互变化时，应评估是否需要补 E2E。

## 何时更新本文档

当以下情况出现时，应回写这里：

- 应用壳层或页面组织规则发生变化
- 新形成一种会被多个页面复用的状态展示模式
- 组件复用边界或共享策略发生调整
