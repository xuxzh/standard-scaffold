# web E2E 测试设计

日期：2026-05-21

## 目标

在现有 `pnpm + turbo` monorepo 中，为 `apps/web` 增加一套独立维护的端到端测试工程 `apps/web-e2e`，用于验证浏览器级真实用户流程。

首期目标如下：

- 使用 `Playwright` 建立可运行的 E2E 测试基础设施
- 将测试工程与 `apps/web` 业务代码解耦，避免混放在同一个 workspace
- 首批覆盖 `导航主链路` 与 `界面状态`
- 优先支持本地前端独立运行
- 后续在不重建框架的前提下扩展到联调环境

## 范围

本次设计包含：

- `apps/web-e2e` 的目录结构
- `Playwright` 配置策略
- 本地独立模式与联调模式的共存方式
- 首批测试用例边界
- 稳定性与可维护性约束

本次设计不包含：

- 真实鉴权、账号体系与测试数据平台的落地实现
- 跨多个应用或多个系统的统一平台级验收测试
- 视觉快照体系与截图基线治理
- 大规模接口 mock 平台建设

## 背景

当前仓库主要结构如下：

- `apps/web`：Vite + React + TypeScript 应用
- 根目录使用 `pnpm workspace` 和 `turbo` 管理多包任务
- 当前已有 `Vitest` 单元测试与组件测试基础

现阶段尚未接入浏览器级 E2E 测试框架，因此对于以下需求缺少稳定保障：

- 路由默认跳转是否正确
- 后台布局壳是否正常渲染
- 侧边栏导航切换是否正常
- 独立页面与壳内页面是否按预期显示
- 主题切换与语言切换等用户可见状态是否生效

同时，后续存在与联调环境结合的需求，因此当前方案不能只针对本地演示场景，而需要保留向 `staging` 或测试环境平滑扩展的能力。

## 方案选择

本次采用以下方案：

- 在 `apps` 下新增独立 workspace：`apps/web-e2e`
- 使用 `Playwright` 作为唯一 E2E 框架
- 让 `apps/web-e2e` 持有测试依赖、配置、页面对象、fixtures 和测试用例
- 让 `apps/web` 继续只承担被测应用职责，不混入 E2E 代码
- 通过环境配置在同一套测试代码上支持 `local` 与 `staging` 两种模式

选择该方案的原因如下：

- `apps/web-e2e` 与 `apps/web` 的 ownership 清晰，符合 monorepo 中按边界组织 workspace 的方式
- `Playwright` 在真实浏览器自动化、网络拦截、trace、截图和多环境运行方面更适合当前与后续需求
- 同一套测试资产既能满足“前端独立”阶段，也能逐步扩展到联调环境，避免后期重写

## 目录设计

推荐新增如下目录结构：

```text
apps/
  web/
  web-e2e/
    package.json
    playwright.config.ts
    tsconfig.json
    .env.example
    tests/
      navigation.spec.ts
      ui-state.spec.ts
    pages/
      app-shell.page.ts
      settings.page.ts
    fixtures/
      test.ts
    helpers/
      env.ts
      routes.ts
      storage.ts
    mocks/
      handlers.ts
```

目录职责如下：

- `tests/`：按用户流程组织测试用例
- `pages/`：封装页面对象与高频交互
- `fixtures/`：封装共享测试上下文和启动逻辑
- `helpers/`：封装环境判断、路由常量、状态读取等工具
- `mocks/`：仅存放前端独立模式下必需的 mock 逻辑

该结构的核心原则是让 E2E 作为一个独立应用单元存在，而不是把测试文件零散附着在被测应用目录中。

## Workspace 与脚本设计

`apps/web-e2e` 应作为一个独立 workspace，具备自己的 `package.json` 与脚本。

建议提供以下脚本：

- `test:e2e`：本地无头执行
- `test:e2e:ui`：Playwright UI 模式
- `test:e2e:headed`：有头执行，便于本地排查
- `test:e2e:debug`：调试模式执行
- `test:e2e:staging`：联调环境执行

根目录可补充聚合入口，例如：

- `pnpm --filter @repo/web-e2e test:e2e`

`turbo` 中可将 E2E 视为独立任务，但首期不建议默认纳入每次 `build` 或日常开发全量任务链路中。

建议的执行节奏如下：

- 本地开发时手动运行指定 spec
- PR 或合并前运行核心 smoke 用例
- 联调阶段或定时任务中运行完整 E2E 集合

## 运行模式设计

同一套测试代码支持两种运行模式：

### 本地独立模式

- 默认模式
- 由 `Playwright webServer` 自动启动 `apps/web`
- `baseURL` 指向本地开发地址
- 如页面不依赖真实后端，则直接测试真实前端页面
- 如页面依赖接口，则使用最小必要的浏览器层 mock 保证主流程稳定

### 联调模式

- 不启动本地 `apps/web`
- 从环境变量读取外部 `baseURL`
- 关闭本地 mock，改为访问测试环境真实接口
- 后续再逐步补齐账号、鉴权态、测试数据准备与清理能力

设计要求如下：

- spec 与页面对象尽量不因环境不同而分叉
- 环境差异应尽量收敛在配置、fixtures 与 mock 开关中
- `local` 与 `staging` 的切换应基于环境变量，而不是复制两套测试工程

## Playwright 配置策略

首期 `playwright.config.ts` 建议采用以下原则：

- 浏览器仅启用 `chromium`
- 启用失败截图与录屏
- 启用 `trace: on-first-retry`
- 本地与 CI 使用不同的重试策略
- 默认超时保持适中，避免用过长超时掩盖环境问题

配置意图如下：

- 首期优先追求稳定、可调试和可快速落地
- 暂不追求多浏览器矩阵覆盖
- 待主流程稳定后，再评估是否补充 `webkit` 和 `firefox`

## 首批测试用例设计

首批只覆盖两类核心流程。

### navigation.spec.ts

覆盖以下行为：

- 打开 `/`
- 验证默认重定向到首页
- 验证后台壳的顶部栏、侧边栏、内容区渲染成功
- 通过侧边栏跳转到壳内页面
- 直接访问独立页面并验证不展示后台壳

### ui-state.spec.ts

覆盖以下行为：

- 切换主题并验证关键状态生效
- 切换语言并验证页面文案或标题变化
- 刷新页面后验证主题与语言状态是否按产品预期保留

首批用例不包含：

- 登录、登出、权限跳转
- 复杂表单提交流程
- 视觉快照比对
- 大量业务接口流程

## 页面对象设计

为减少重复与提升可维护性，推荐引入页面对象层。

首期建议至少包含：

- `AppShellPage`：封装后台壳访问、侧边栏导航、壳内区域断言
- `SettingsPage` 或等价页面对象：封装主题切换、语言切换等交互

页面对象的职责如下：

- 封装稳定交互动作
- 封装高频断言
- 屏蔽选择器细节

页面对象不应承担业务编排之外的复杂状态机逻辑，保持轻量即可。

## 选择器与稳定性约束

为降低 E2E 脆弱性，需要提前约束页面可测试性。

建议遵循以下规则：

- 优先使用语义角色选择器
- 其次使用稳定文案
- 对关键控件补充 `data-testid`
- 不依赖 Tailwind 类名或脆弱 DOM 层级

首批建议为以下元素提供稳定识别方式：

- 主题切换入口
- 语言切换入口
- 侧边栏主导航项
- 后台壳根节点
- 独立页面根节点

此外，断言策略应尽量面向用户行为结果，而不是内部实现细节。例如：

- 对导航流程，断言 URL 与页面主标题
- 对独立页，断言后台壳不存在
- 对主题切换，断言根节点主题属性或等价稳定标识变化

## Mock 策略

本地独立阶段允许使用最小必要 mock，但需要保持约束。

约束如下：

- 仅在页面确实依赖接口时引入 mock
- mock 目标是稳定主流程，不是重建完整后端
- mock 逻辑集中在 `mocks/` 与 fixtures 中，不散落在各 spec
- 能不用 mock 的页面优先直接走真实前端逻辑

该约束可以避免测试维护成本快速上升，也能为后续切换到联调环境保留一致的用例结构。

## 环境变量设计

建议在 `apps/web-e2e` 中维护独立环境变量约定，例如：

- `E2E_MODE=local|staging`
- `E2E_BASE_URL=...`

设计要求如下：

- 本地模式默认值尽量开箱即用
- 联调模式必须显式提供环境地址
- 环境识别逻辑集中在 `helpers/env.ts`

这样可以避免在多个 spec 中重复判断运行环境。

## CI 与报告设计

E2E 首期建议采用轻量接入方式。

- 本地支持单个 spec、单个测试快速执行
- PR 阶段仅运行核心 smoke 集合
- 每日构建或联调阶段再运行全量 E2E
- 失败时保留 HTML report、trace、截图、录屏

对于联调环境，需要接受一段时间内环境波动带来的不稳定，因此：

- 前期不要把所有联调用例都作为强制门禁
- 先将本地主流程 smoke 作为最早的稳定门禁

## 成功标准

当以下条件满足时，认为本次设计目标达成：

- 新增 `apps/web-e2e` 作为独立 workspace
- `Playwright` 可在本地启动并访问 `apps/web`
- 首批包含 `navigation.spec.ts` 与 `ui-state.spec.ts`
- 支持基于环境变量切换 `local` 与 `staging`
- 关键交互具备稳定选择器与可维护断言方式
- 报告、trace 和失败排障信息可用

## 后续实现边界

本设计完成后，下一阶段实现计划应聚焦以下内容：

- 创建 `apps/web-e2e` workspace 基础文件
- 安装并配置 `Playwright`
- 接入 `pnpm workspace` 与 `turbo` 脚本
- 补充 `apps/web` 关键页面稳定选择器
- 实现首批两个 spec 与页面对象
- 验证本地运行链路

联调环境相关内容可在首期本地链路稳定后作为下一轮增量实施。
