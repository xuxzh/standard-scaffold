# Web 多语言适配规范

本文档定义 `apps/web` 的多语言开发默认规则。它服务于日常功能开发和 AI 执行，回答“新增或修改用户可见文案时应该怎样做”。

## 基线

- 当前 Web 应用使用 `i18next` 和 `react-i18next`。
- 国际化配置与资源集中在 `apps/web/src/i18n`。
- 当前默认支持 `zh-CN` 和 `en-US`。
- 历史设计背景见 `docs/specs/2026-05-21/web-i18n-design.md`。

## 文案接入规则

- 用户可见文案必须通过 i18n 资源获取，不要在组件、页面、hook、service 或测试数据中直接写中文或英文业务文案。
- 新增或修改用户可见文案时，必须同步维护 `zh-CN` 和 `en-US` 资源。
- 文案 key 使用语义化层级命名，不使用英文原文作为 key。
- 代码中的稳定值、枚举值、接口字段、路由路径和测试标识继续使用英文稳定值，不应翻译成展示文案。
- 组件中优先使用 `useTranslation()` 获取文案；不要新增平行的字典、Context 或自定义翻译状态。

## 资源组织规则

- 词条按现有 locale 与 namespace 结构组织：`apps/web/src/i18n/resources/<locale>/<namespace>.ts`。
- 通用动作、应用壳层、跨页面状态文案优先放入 `common`。
- 业务功能文案优先放入对应功能已有 namespace；没有合适 namespace 时，应按功能边界新增，而不是把大量业务词条塞进 `common`。
- 新增 namespace 时，需要同步更新 `apps/web/src/i18n/config.ts` 中的资源注册。
- 不要为单个组件创建一次性 namespace，除非该组件本身是稳定的跨功能能力。

## UI 与交互规则

- 语言切换入口沿用现有 `LanguageToggle` 和应用壳层接入方式。
- 不要调整 i18n provider 与 theme、router 等全局 provider 的顺序，除非有明确设计和验证。
- 不使用国旗表达语言，避免把语言和国家绑定。
- 切换语言后，当前页面上的用户可见文案应即时更新。

## 测试与验证

- 测试优先断言用户可见行为，而不是词条文件内部结构。
- 新增关键页面、应用壳层、导航、弹窗或表单文案时，至少覆盖默认语言下的主要可见文案。
- 涉及语言切换、语言持久化、fallback 或资源注册变更时，应补充对应 Vitest 或 E2E 覆盖。
- 修改用户可见文案后，应至少运行受影响范围的 `apps/web` 测试或静态检查。
- 做代码审查时，应检查是否存在新增硬编码中文、遗漏英文资源、直接展示 i18n key 或只维护单一语言资源。

## 非目标

- 本规范不引入在线翻译平台、远程词条下发或新的国际化技术栈。
- 本规范不要求一次性清理所有历史文案；新改动应从触达范围内保持一致。
- 日期、数字、货币等本地化格式化规则如需扩展，应先补充单独设计或规范。
