# 工程规范

这个目录用于沉淀仓库内长期有效的代码与工程实现约束，回答的是“默认应该怎样写、怎样组织、怎样验证”，而不是“某次任务具体改哪几行”。

## 适合放什么

- 目录、命名、模块边界规范
- React、route、feature、hooks 的职责划分
- 数据访问与状态管理约束
- 测试分层、验证基线和完成定义补充规则
- 文档回写和变更边界的通用规范

## 不适合放什么

- 单次任务的实现步骤
- 一次性缺陷分析过程
- 已经被工具完整表达、且没有例外说明价值的纯机械规则

单次任务应继续写入 `docs/plans/` 或 `docs/specs/`；工具已严格覆盖的规则，应以 ESLint、TypeScript、测试和脚本为准。

## 与其他文档的边界

- `AGENTS.md`：高频硬约束入口
- `docs/ai/`：AI 工作流、模板、清单和运行手册
- `docs/api/`：远程接口契约与集成约束
- `docs/ui/`：界面与交互约束
- `docs/adr/`：长期决策原因

这个目录负责的是代码实现层面的默认做法与例外边界。

## 首批文档

- `web-code-guidelines.md`：当前 Web 应用实现规范
- `web-business-module-guidelines.md`：Web 业务模块目录、边界和验证规范
- `web-i18n-guidelines.md`：Web 多语言适配与词条维护规范

## 维护规则

- 当某种实现约束被多个任务反复使用时，抽取到这里。
- 当规范背后的长期方向变化时，先用 ADR 记录原因，再回写这里。
- 文档不应与 lint、类型系统或测试脚本长期漂移；一旦发现分歧，应优先修正基线而不是保留冲突表述。
