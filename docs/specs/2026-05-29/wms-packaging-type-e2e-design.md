# WMS 包装类型页面 E2E 设计

## 背景

当前 `apps/web-e2e` 已覆盖后台壳导航、界面状态和基于 API mock 的基础业务页面可达性，但还没有任何面向 WMS 包装模块的完整业务流程测试。

包装类型页面已经具备查询、新增、编辑、单条删除、批量删除和导出等能力，适合作为包装模块第一张业务页落地 E2E。此次工作不仅要补齐包装类型页面的核心 CRUD 端到端测试，还需要为后续新增包装规格、包装层级、包装规则等包装模块页面预留清晰的测试组织方式，避免首批用例直接演变为无法复用的单页脚本。

## 目标

- 为包装类型页面建立可稳定运行的核心 CRUD E2E 用例。
- 在 `apps/web-e2e` 内按 WMS/包装业务域建立可扩展目录结构。
- 复用现有 API mock 运行方式，让包装类型业务流程可以在本地模式稳定执行。
- 仅在必要处补充稳定选择器和页面对象封装，为后续整个包装模块的 E2E 扩展奠定基础。

## 非目标

- 本次不覆盖导出、导入、列设置、刷新等辅助能力。
- 本次不为整个包装模块一次性抽象通用 CRUD 基类或复杂 fixture 体系。
- 本次不接入真实后端联调数据准备流程，仍以本地模式和 API mock 为主。
- 本次不重构现有 `apps/web-e2e` 的全部目录，只在包装模块相关范围内增量扩展。
- 本次不新增 Playwright 以外的测试基础设施。

## 范围级别

- 建议任务级别：`L2`
- 原因：改动跨越 `apps/web` 与 `apps/web-e2e`，涉及业务页面稳定标识、mock 数据行为、页面对象设计和多条端到端流程，但边界仍集中在单一业务页及其所在测试工程，复杂度中等且可分阶段验证。

## 受影响边界

- `apps/web-e2e/tests/*`
  - 新增按 `wms/packaging` 分层的业务 spec，避免继续把所有业务流程堆在根级 `tests/` 下。
- `apps/web-e2e/pages/*`
  - 新增包装类型页面对象，封装筛选、表单、勾选和确认删除等高频稳定交互。
- `apps/web-e2e/fixtures/test.ts`
  - 视复用价值决定是否注册包装类型页面 fixture；如果注册，保持 fixture 只负责实例化页面对象，不承载业务行为。
- `apps/web-e2e/helpers/routes.ts`
  - 复用既有包装类型路由常量；后续包装模块页面继续在同一常量文件中追加。
- `apps/web/src/test/msw-handlers.ts` 及相关 mock 支撑
  - 补齐包装类型新增、编辑、删除、批量删除所需的 API mock 行为，保证 E2E 流程可闭环执行。
- `apps/web/src/features/wms/packaging/packaging-type/*`
  - 必要时补充 `data-testid` 或无障碍语义，确保 Playwright 使用稳定选择器而不是脆弱 DOM 结构。

## 建议方案

### 1. 按业务域扩展 `web-e2e` 目录

本次不继续把包装类型 spec 放在 `apps/web-e2e/tests/` 根目录，而是新建 `tests/wms/packaging/packaging-type.spec.ts`，同步新增 `pages/wms/packaging/packaging-type.page.ts`。

这样做的原因：

- 与 `docs/business/wms/packaging/*` 的业务域结构一致，便于从文档映射到用例。
- 后续包装模块新增第二张、第三张业务页时，可以直接在同一目录追加 spec 和页面对象，不需要再次迁移。
- 页面对象边界清晰，避免把包装类型专有交互写进全局 `AppShellPage`。

### 2. 页面对象只封装包装类型页语义

新增 `PackagingTypePage` 页面对象，职责只覆盖包装类型页面自身的稳定语义操作，例如：

- 打开包装类型页面并等待列表可用。
- 填写查询条件并执行筛选。
- 打开新增或编辑抽屉并填写表单。
- 勾选表格行、触发批量删除、确认删除。
- 断言指定编码或名称的记录存在或不存在。

不在首版抽象通用 CRUD 基类，原因是当前包装模块只有一张页面进入 E2E，过早抽象会把真实差异隐藏在泛化接口里，反而增加维护成本。只有当包装模块第二个页面出现明显重复后，再把表格选择、确认删除等能力下沉到共享对象或 helper。

### 3. 首批只覆盖核心 CRUD 用户行为

首批包装类型 E2E 用例聚焦 5 类可见行为：

1. 页面加载后显示包装类型标题和初始列表数据。
2. 按类型编码、类型名称或循环包装状态筛选数据。
3. 新增包装类型后，列表中出现新记录。
4. 编辑现有包装类型后，列表展示更新结果。
5. 单条删除和批量删除后，列表中对应记录消失。

导出虽然已经在页面中实现，但它依赖文件下载、浏览器上下文和更细粒度的数据准备，会显著扩大首批范围；因此本次明确排除，后续可以在包装模块 E2E 第二阶段单独补充。

### 4. 以 mock 闭环支撑可重复执行

当前仓库已经存在 API mock 模式，包装类型的基础查询也已有冒烟覆盖。本次继续沿用这条路径，但要把 mock 从“只返回固定初始列表”扩展为“支持内存态增删改查”。

建议让包装类型相关 mock 具备以下行为：

- 每次测试开始时重置到稳定初始数据。
- 查询接口读取当前内存数据并支持按页面已有过滤条件返回结果。
- 新增接口向内存数据插入新记录并回传成功结果。
- 编辑接口按 `Id` 和 `NeedUpdateFields` 更新内存数据。
- 单删和批删接口从内存数据中移除对应记录。

这样可以让 Playwright 真正验证前端与 mock API 的交互闭环，而不是只断言表单是否关闭、按钮是否可点。

### 5. 优先使用稳定语义选择器，必要时补 `data-testid`

测试选择器优先级保持仓库既有约定：

- `getByRole`
- 稳定文案
- `data-testid`

对于下列容易受文案或 DOM 结构影响的交互，允许在 `apps/web` 内补最小稳定标识：

- 包装类型查询表单根节点或查询按钮。
- 新增/编辑抽屉中的提交按钮与关键字段输入。
- 表格行选择框、单行编辑/删除操作入口。
- 批量删除确认入口。

新增标识要遵循“只为高价值交互补充、命名可复用”的原则，不要把整页每个节点都打上测试 id。

## 备选方案

### 方案 A：直接在单个 spec 中完成所有交互

- 优点：实现速度快，改动文件少。
- 缺点：页面交互、选择器和断言全部堆在 spec 中，后续扩展包装模块时复用性差。

### 方案 B：先做全局通用 CRUD 页面对象体系

- 优点：理论上可服务更多业务页。
- 缺点：当前只有包装类型进入 E2E，抽象依据不足，容易形成过度设计。

### 方案 C：首批只保留列表加载和新增成功的冒烟链路

- 优点：落地最快，验证成本最低。
- 缺点：无法覆盖删除、编辑、筛选这些最容易回归的业务能力，也无法充分检验 mock 是否支持真实流程。

本次不采用以上方案，优先选择“按包装业务域分层 + 包装类型页面对象 + 核心 CRUD 闭环”的中间路径。

## 用例设计

建议首批 spec 覆盖以下场景：

- `loads packaging type list`
  - 进入包装类型页，验证标题、后台壳和至少一条初始 mock 数据可见。
- `filters packaging types by query criteria`
  - 输入查询条件并执行筛选，只保留符合条件的记录。
- `creates a packaging type`
  - 打开新增抽屉，填写类型编码、类型名称、循环包装和描述，提交后验证成功反馈与新记录出现。
- `updates a packaging type`
  - 对初始数据执行编辑，提交后验证更新后的名称、循环包装状态或描述出现在列表中。
- `deletes packaging types from row action and bulk action`
  - 先覆盖单条删除，再覆盖批量删除，验证确认后对应记录消失。

如果实现中发现单条删除和批量删除共享大量准备步骤，可以拆成两个用例，但仍保持它们位于同一包装类型 spec 中。

## 数据流

1. Playwright 在本地模式启动 `apps/web`，并通过初始化脚本写入最小登录态。
2. 用户访问 `appRoutes.packagingType`，后台壳和包装类型页面加载。
3. 页面调用包装类型查询接口，从 mock 内存数据读取初始列表。
4. 测试通过查询表单、抽屉表单和表格操作驱动页面行为。
5. 页面分别调用新增、编辑、删除、批量删除接口，mock 内存数据同步变化。
6. React Query 或页面刷新逻辑重新拉取列表，界面反映最新 mock 数据。
7. Playwright 断言用户可见结果，而不是直接断言内部实现细节。

## 验证计划

- `pnpm --filter @repo/web test`
- `pnpm --filter @repo/web typecheck`
- `pnpm --filter @repo/web-e2e exec playwright test --list`
- `pnpm --filter @repo/web-e2e test:e2e tests/wms/packaging/packaging-type.spec.ts --project=chromium`

完成时需要给出以下验证证据：

- 新增 spec 已出现在 Playwright 测试清单中。
- Web 应用单测或相关测试未因 mock 与稳定选择器调整而回归。
- 包装类型 spec 在本地模式下可通过，且覆盖页面加载、筛选、新增、编辑、删除主流程。

## 风险

- 如果当前 MSW mock 结构不支持跨请求共享内存状态，CRUD 用例会出现“提交成功但列表未变”的假失败，需要优先梳理 mock 状态重置策略。
- 如果页面上的关键交互缺少稳定语义，测试容易过度依赖图标按钮或脆弱 DOM 结构，后续 UI 微调时会频繁失效。
- 如果把太多包装模块共性提前抽象为基类，首批实现会变慢，且后续真实页面差异可能反过来推倒抽象。
- 删除确认依赖 `window.confirm`，如果现有实现未来切换成自定义对话框，页面对象需要保留足够清晰的确认入口适配空间。
