# 后台壳头像菜单与退出登录设计

## 背景

当前后台壳已经具备登录态校验、Token 持久化、语言切换和主题切换能力，但头部还没有用户入口，用户无法在壳层内看到自己的登录身份，也没有显式的退出登录操作。

这次变更目标是补齐一个最小但完整的用户入口闭环：在壳层头部展示头像按钮，菜单中显示当前用户名，并提供带二次确认的退出登录能力。

## 目标

- 在后台壳头部新增用户头像入口。
- 点击头像后展示下拉菜单，菜单顶部显示用户名。
- 菜单中提供退出登录操作，并在执行前要求用户确认。
- 退出后清理本地登录态并跳转到登录页。
- 用户信息展示和交互文案同时支持 `zh-CN` 与 `en-US`。

## 非目标

- 不接入真实用户资料查询接口。
- 不实现用户中心、个人设置、修改密码或切换租户。
- 不展示真实头像图片 URL，本次仅使用字符头像占位。
- 不重构现有认证体系，不引入全局认证上下文。
- 不改动侧边栏结构，不把用户入口迁移到其他区域。

## 范围级别

- 建议任务级别：`L1`
- 原因：改动集中在壳层头部、轻量本地状态和登录退出闭环，数据流简单，不涉及新的后端契约和复杂跨模块设计。

## 受影响边界

- `apps/web/src/components/layout/app-header.tsx`
  - 头部增加用户菜单入口。
- `apps/web/src/components/layout/*`
  - 新增用户菜单组件及退出确认弹层。
- `apps/web/src/components/ui/*`
  - 复用现有 `dropdown-menu` 与 `dialog` 基础组件，不新增新的通用 UI 体系。
- `apps/web/src/features/auth/login-page.tsx`
  - 登录成功后额外写入轻量用户展示信息。
- `apps/web/src/lib/auth/*`
  - 新增或扩展用户展示信息的读写与清理能力。
- `apps/web/src/i18n/resources/*`
  - 增补头像菜单和退出确认相关文案。
- `apps/web/src/app.test.tsx`
  - 补充头部用户入口与退出登录流程测试。

## 建议方案

### 1. 轻量用户展示信息存储

在认证相关目录下新增轻量用户展示信息存储，职责仅限：

- 保存用户展示信息
- 读取用户展示信息
- 清理用户展示信息

首版数据结构保持最小：

- `userCode`
- `displayName`

其中 `displayName` 首版直接取登录时输入的 `userCode`，避免引入额外的后端依赖。后续如果接入真实用户资料接口，只需要替换写入来源，不需要改动头部菜单的消费方式。

### 2. 登录成功时写入用户展示信息

登录页在现有 `setAuthToken()` 之后，再调用轻量用户展示信息写入逻辑。

首版约束：

- `userCode` 使用登录表单输入值
- `displayName` 同样使用 `userCode`
- 不做额外昵称映射规则

这样可以保证：

- 测试环境和真实行为一致
- 刷新页面后头像菜单仍能拿到用户名
- 将来的用户资料扩展不会影响当前登录闭环

### 3. 头部用户菜单

`AppHeader` 保持“壳层头部布局组件”定位，不承载过多业务逻辑。建议新增独立 `UserMenu` 组件并在头部右侧组合使用。

`UserMenu` 的结构：

- 头像按钮作为触发器
- 下拉菜单顶部显示用户名
- 菜单操作区先只保留一个 `退出登录`

头像按钮展示规则：

- 有用户名时，用用户名首字母作为字符头像
- 没有用户名时，使用稳定默认占位字符
- 触发器保留无障碍名称，避免只有视觉头像没有可读语义

本次不展示头像 URL、不显示用户编码第二行，也不在菜单里加入额外操作，保证入口足够轻量。

### 4. 退出登录确认流程

点击下拉菜单中的 `退出登录` 后，不直接执行跳转，而是先关闭菜单并打开确认弹层。

确认弹层复用现有 `dialog` 基础组件，包含：

- 标题
- 说明文案
- `取消`
- `退出登录`

执行顺序固定为：

1. 清理轻量用户展示信息
2. 清理 Token 信息
3. 跳转到登录页

跳转时保留当前页面作为 `redirect`，这样用户重新登录后仍可回到退出前页面；如果当前已在登录页，则沿用现有重定向保护逻辑避免重复跳转。

### 5. 缺省与异常处理

- 如果本地只有 Token 没有用户展示信息，头部仍然渲染头像按钮，使用默认占位字符。
- 如果用户展示信息缺失，菜单顶部回退到通用占位名称，不阻断页面使用。
- 退出时即使用户展示信息不存在，也应继续清理 Token 并完成跳转。

本次不增加退出 API，也不引入失败重试逻辑；退出动作完全是前端本地会话清理。

## 备选方案

### 方案 A：只额外存一个 `userCode`

- 优点：实现最少。
- 缺点：后续加入昵称、头像 URL 或组织信息时容易继续堆在零散字段上，演进性较差。

### 方案 B：直接构建完整认证上下文

- 优点：长期结构更完整。
- 缺点：对本次需求明显过重，会把一个壳层小功能扩展为认证体系重构。

本次不采用这两种方案，优先选择“轻量用户展示信息存储 + 独立用户菜单组件”的中间路径。

## 数据流

1. 用户在登录页提交 `userCode` 和 `password`。
2. 登录成功后保存 Token。
3. 同步保存轻量用户展示信息。
4. 用户进入后台壳时，头部 `UserMenu` 从本地存储读取展示信息。
5. 用户点击头像，打开下拉菜单查看用户名。
6. 用户点击 `退出登录`，打开确认弹层。
7. 用户确认后，前端清理用户展示信息和 Token，并跳转到登录页。

优先补充最小但有效的测试：

- 已登录时头部出现头像入口
- 菜单中可见用户名
- 点击退出登录后出现确认弹层
- 确认退出后跳回登录页并清空本地登录态

## 风险

- 现有测试辅助如果只写入 `accessToken`，会与真实登录成功后的本地状态不一致，需要同步补齐最小 token 与用户展示信息。
- 用户名首字母回退规则如果处理空字符串不严谨，可能出现空头像按钮，需要提供稳定默认值。
- 头部新增交互后，如果无障碍名称缺失，测试和真实读屏体验都会变差。
