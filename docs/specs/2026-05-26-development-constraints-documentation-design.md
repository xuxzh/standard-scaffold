# 开发约束文档体系设计

日期：2026-05-26

## 目标

为当前仓库补齐一套用于约束开发行为的长期文档体系，使接口规范、UI 规范、代码规范和工程约定有稳定入口，并与现有的 `AGENTS.md`、`docs/ai`、`docs/specs`、`docs/plans`、`docs/adr` 形成清晰分工。

这套文档体系的目标不是增加额外流程，而是降低以下问题的发生概率：

- 规则只存在于聊天记录或口头约定中
- AI 或开发者重复在相同问题上做不一致决策
- 某类规范没有固定落点，后续只能继续往 `AGENTS.md` 堆细节
- 设计文档、长期规范和执行计划相互混放，导致检索成本上升

## 非目标

第一阶段不追求以下目标：

- 不在本次设计中引入 Storybook、设计平台或 OpenAPI 生成链路
- 不把所有已有设计文档迁移到新目录
- 不把工具可自动约束的规则全部重复写成文档
- 不让规范目录替代 ESLint、TypeScript、测试和脚手架本身

## 设计原则

### 1. 按“约束类型”而不是“作者视角”分层

约束开发的文档应按其约束对象组织，而不是按“AI 文档”“前端文档”“后端文档”混合堆放。这样能让人和 AI 在遇到具体问题时，优先定位到对应约束域。

### 2. 高频硬约束放入口，细则下沉

`AGENTS.md` 和 `docs/ai/context-index.md` 继续承担入口职责，只保留必须先读、跨任务通用、短小稳定的规则。详细规范应下沉到专门目录，入口文件只做索引和摘要。

### 3. 长期规范与单次设计分离

单次任务的设计与边界继续放在 `docs/specs`；长期有效、可复用的规范单独归档，避免后续 AI 把某次方案误当成仓库总规则。

### 4. 能工具化的规则优先工具化

代码规范、类型约束、测试约束等，优先由 ESLint、TypeScript、测试基线和脚手架约束表达。文档主要记录工具无法完整表达的判断依据、边界和例外。

## 目录设计

建议在 `docs/` 下新增以下长期目录：

### `docs/api/`

用于记录接口契约与集成约束，面向“如何与远程能力对接”。适合收纳：

- API 设计原则与字段命名约定
- 请求参数、响应结构、分页和筛选规则
- 错误模型与错误码约定
- 鉴权头、时区、幂等、排序等通用约束
- OpenAPI 文件或其人工维护版本的入口说明

### `docs/ui/`

用于记录用户界面和交互规范，面向“界面应该怎样被组织与实现”。适合收纳：

- 设计 token 使用规则
- 页面布局和壳层约束
- 组件状态规范，如 loading、empty、error、disabled
- 文案、密度、表格、表单等通用 UI 模式
- 本地组件与共享组件的使用边界

### `docs/standards/`

用于记录代码与工程实现约束，面向“代码应该如何写、如何组织、如何验证”。适合收纳：

- 命名、目录、模块边界规范
- React 组件组织方式
- 数据访问分层约束
- 测试分层与验证基线
- 文档回写、变更分级、提交流程补充规范

## 与现有目录的分工

### `AGENTS.md`

继续作为仓库级高频硬约束入口。它不承载全部细则，而是保留摘要式规则，并链接到 `docs/api/`、`docs/ui/`、`docs/standards/` 中的详细规范。

### `docs/ai/`

继续承载 AI 工作流、入口、模板、运行手册和检查清单，不负责存放业务接口规范、UI 规范或通用代码规范的正文。

### `docs/specs/`

继续承载单次设计文档，例如“某个能力如何设计”“某次中等风险改动的边界是什么”。如果某份设计最终上升为长期规则，再抽取稳定部分沉淀到 `docs/api/`、`docs/ui/` 或 `docs/standards/`。

### `docs/plans/`

继续承载执行计划，不承载长期约束正文。

### `docs/adr/`

继续承载长期决策。它回答“为什么采用这条方向”，而 `docs/api/`、`docs/ui/`、`docs/standards/` 回答“默认应该怎么做”。

## 第一阶段文档清单

第一阶段不需要一次性写很多文档，优先补齐最容易成为开发约束入口的最小集合。

### `docs/api/README.md`

说明 API 文档目录职责、文档边界和推荐维护方式。

### `docs/api/http-contract-guidelines.md`

定义 Web 应用对接接口时的通用约定，至少包括：

- 请求与响应命名风格
- 分页、筛选、排序字段约定
- 错误结构约定
- 日期时间与时区处理约定
- 前端 `contract -> service -> route/component` 的衔接关系

### `docs/ui/README.md`

说明 UI 文档目录职责、规范适用范围，以及与 `apps/web/src/components/ui`、`packages/ui` 的边界。

### `docs/ui/application-ui-guidelines.md`

定义当前脚手架的 UI 约束，至少包括：

- `AdminLayout`、`AppHeader`、`AppSidebar` 的壳层约束
- 本地 UI 基础组件与共享组件的使用优先级
- 页面常见状态的展示规范
- 交互与可访问性最低要求

### `docs/standards/README.md`

说明工程规范目录职责，以及哪些规则应该由工具表达、哪些规则应该由文档表达。

### `docs/standards/web-code-guidelines.md`

定义当前 Web 应用实现规范，至少包括：

- `@/` 别名与目录组织约定
- React 组件、hooks、route、feature 的职责边界
- 数据访问分层约束
- 状态管理与 React Query 的使用边界
- 局部验证和完成定义入口

## 文档导航规则

为避免新目录建出来后仍然难找，第一阶段应同步补三处入口导航：

1. 在 `docs/ai/context-index.md` 的“主要模块地图”或“文档回写规则”附近加入新目录入口
2. 在 `docs/ai/README.md` 的“目录说明”中补充约束文档目录说明
3. 在 `AGENTS.md` 中补一小节“开发约束文档”，只列入口，不展开正文

## 命名与维护规则

### 文档命名

- 目录首页统一使用 `README.md`
- 长期规范文档使用语义化英文文件名，避免日期前缀
- 单次设计和实施计划继续沿用现有日期前缀规则

### 内容粒度

- 每份规范文档只承担一种主要职责
- 优先写“默认做法”和“例外条件”，少写空泛原则
- 规则需要尽量指向现有代码锚点或目录锚点

### 演进方式

- 当某次任务设计中的规则被证明可复用时，抽取到长期规范目录
- 当长期规范背后的方向发生变化时，用 ADR 记录决策原因
- 当规则已被 ESLint、TS 或脚本完整覆盖时，文档只保留简短说明和入口

## 推荐实施顺序

第一阶段建议按以下顺序落地：

1. 创建 `docs/api/`、`docs/ui/`、`docs/standards/`
2. 为每个目录写 `README.md`
3. 为每个目录补一份首批核心规范文档
4. 更新 `docs/ai/context-index.md`
5. 更新 `docs/ai/README.md`
6. 更新 `AGENTS.md`

这能保证新目录一出现就具备可导航性，而不是只建空目录。

## 验收标准

当以下条件成立时，可认为第一阶段完成：

- 仓库中存在 `docs/api/`、`docs/ui/`、`docs/standards/` 三类长期规范目录
- 每个目录至少有一个入口文档和一个可直接使用的首批规范文档
- `AGENTS.md`、`docs/ai/context-index.md`、`docs/ai/README.md` 已能把人或 AI 导航到这些文档
- 现有 `docs/specs`、`docs/plans`、`docs/adr` 的职责未被新目录稀释或替代

## 风险与取舍

如果把这些规范继续追加到 `docs/specs`，短期成本最低，但长期会让“单次设计”和“仓库长期规则”混在一起，AI 和人工都更容易误读。

如果把全部细则都塞进 `AGENTS.md`，入口会越来越重，更新成本上升，而且很多细节并不适合要求每次会话都先读。

因此，推荐方案是在 `docs/` 下新增长期规范目录，并让入口文件只保留摘要和跳转。
