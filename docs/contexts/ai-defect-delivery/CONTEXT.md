# AI 缺陷交付

本上下文描述从缺陷确认、AI 修复到测试环境验收的核心业务语言。它只定义领域概念，不记录实现细节。

## Language

**缺陷（Bug）**:
产品或工程行为与明确预期不一致的一项问题。一个缺陷对应一条**修复交付链**。
_Avoid_: 任务、需求、工单

**修复交付链**:
为解决一个**缺陷**而形成的连续交付记录，可以包含多个修复计划、执行运行和 Pull Request。
_Avoid_: 部署、发布批次

**修复计划（Repair Plan）**:
描述修复目标、边界、验证方式和风险的版本化约定。只有获得人工批准的版本才能进入自动修复。
_Avoid_: AI 建议、执行日志

**自动化资格（Automation Eligibility）**:
缺陷修复交付链可以进入的最高自动化阶段。`L0/L1` 可进入完整自动闭环，`L2` 需要正式设计或计划和额外人工批准，`L3` 只能进入人工移交。
_Avoid_: Agent 权限、自动化等级

**自动化禁区（Automation Exclusion）**:
无论初始任务级别如何，都不能由 MVP 自动修改的变更类别，包括依赖、数据库结构与迁移、CI、部署、安全凭据和 AI Manager 自身。
_Avoid_: 普通禁止路径、计划外文件

**人工移交（Manual Handoff）**:
缺陷退出自动修复链并转为独立人工主导任务的结果。已有评估和证据继续保留。
_Avoid_: 自动修复失败、待重试

**交付槽位（Delivery Slot）**:
仓库同一时间授予一条修复交付链的独占修复和可合并资格。多个缺陷可以等待或评估，但只有槽位持有者可以推进修复和合并。
_Avoid_: 文件锁、任务锁

**合并授权（Merge Authorization）**:
管理员对某个精确 Pull Request head Commit 作出的自动合并许可。head Commit 发生变化时授权失效。
_Avoid_: PR 批准、分支授权

**部署（Deployment）**:
将仓库某个 Commit 所代表的整体版本交付到目标环境的一次仓库级事件。一次部署可以覆盖多个缺陷。
_Avoid_: 缺陷部署、Bug 发布

**等待测试环境（Merged Awaiting Staging）**:
缺陷修复已经合并，但当前测试环境成功版本尚未包含其 merge Commit。
_Avoid_: 部署失败、修复失败

**测试环境就绪（Staging Ready）**:
缺陷的 merge Commit 已包含在测试环境当前成功版本中，可以接受人工验收，但不表示缺陷已经解决。
_Avoid_: 已解决、已关闭

**缺陷验收（Bug Acceptance）**:
管理员针对一个**测试环境就绪**的缺陷，确认预期行为是否恢复的独立判断。验收结果属于缺陷，不改变 Deployment 的结果。
_Avoid_: 部署验收、发布验收

**已解决（Resolved）**:
缺陷对应版本已成功部署到测试环境，并由管理员人工确认预期行为已经恢复。
_Avoid_: 已合并、已部署

## Example Dialogue

> 开发：两个缺陷分别合并了，它们各自有一次部署吗？
>
> 领域负责人：没有。部署属于仓库版本，同一次成功部署可以让多个缺陷进入测试环境就绪。
>
> 开发：部署成功后会自动把缺陷标记为已解决吗？
>
> 领域负责人：不会。每个缺陷仍需独立验收。
>
> 开发：修复时发现必须改依赖或数据库迁移，可以重新批准后继续吗？
>
> 领域负责人：不可以。这些属于自动化禁区，需要人工移交。
